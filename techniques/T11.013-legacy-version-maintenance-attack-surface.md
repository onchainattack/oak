# OAK-T11.013 — Legacy-Version Maintenance Attack Surface

**Parent Tactics:** OAK-T11 (Custody and Signing Infrastructure); structurally adjacent to OAK-T9.007 (Fork-Substrate Vulnerability — both involve deployed code that missed fixes, but T9.007 covers a downstream fork of a different protocol; T11.013 covers the same operator's own superseded, deprecated or abandoned component)
**Maturity:** emerging
**Chains:** EVM (primary), with declaring examples also on Cosmos IBC, Solana and multi-chain signing infrastructure; structurally generalisable to any chain where an operator leaves an old component running
**First documented:** 2026-01 (IPOR Fusion legacy PlasmaVault, 2026-01-06; the earliest example that declares this Technique)
**Aliases:** "deprecated-version attack surface", "legacy-version residual vulnerability", "deprecation-without-decommission", "abandoned-but-live contract"

## Description

A superseded, deprecated or abandoned component is left **deployed and reachable** after the operator has moved on, and an attacker uses it. The component may still hold funds, may hold nothing but **standing authority** (approvals or permissions granted during its working life), or may be an off-chain service that can still reach user keys. In each declaring example the loss traces to something that was left running after its replacement shipped, with no one owning its decommissioning or monitoring.

The structural feature is the **missing decommissioning step**, not the vulnerability class. The flaw that is finally used can belong to any T9.x class (an unauthenticated function, an unsafe integer cast, a missing validation), or to none at all (an old approval that was never revoked). The examples show several sub-shapes:

- **Deprecated but still funded.** A superseded version keeps deposits and is reachable, as in Notional Finance V1 and a legacy IPOR Fusion vault.
- **Dormant, holding claimable value.** A 2020 MakerDAO keeper held four never-settled auction lots until a function that never checked its caller was used.
- **Immutable and abandoned.** Aztec's deprecated contracts could not be patched or paused because they are immutable and admin access was relinquished. The mitigation differs from the mutable case: drain reserves before abandonment.
- **Standing admin surface on abandoned infrastructure.** DxSale's 2021-era lockers.
- **Standing authority with no funds.** ether.fi's deprecated AtomicQueue and Limit Break's Payment Processor V2 were used through approvals that users never revoked.
- **Legacy code carried forward.** Secret Network's dropped checks survived a 2026 migration; the THORChain example records a signing-library fork far behind upstream.
- **Off-chain legacy service.** Bullpen's operator said the attacker entered through a "legacy system" tied to early-beta accounts.

Distinct from sibling Techniques:

- **T9.007 (Fork-Substrate Vulnerability Not Mitigated)** — Protocol B forks Protocol A and fails to track upstream patches. T11.013 concerns the **same operator's own** older component. The gap in T9.007 is between two teams; in T11.013 it is inside one team's version-lifecycle management.
- **T9.004 (Access Control Misconfiguration)** — the access-control flaw itself. Several T11.013 examples also declare T9.004 for the mechanical flaw; T11.013 records why the flawed or over-permissioned component was still reachable.
- **T6.007 (Trust-substrate Shift / Vendor-side Promise Revocation)** — the operator changes a policy promise. T11.013 involves no policy change.
- **T11.005 (Operator-Side Fake-Platform Fraud)** — the operator is fraudulent. In T11.013 the operator is genuine; the failure is in decommissioning.

## Observed indicators

- **A replaced component still deployed.** The old version, keeper, queue, locker or service is still live after its replacement shipped (Notional V1 after V2; the MakerDAO keeper after 2020; Magic Eden's stop of routing through Payment Processor V2 in October 2024).
- **Value or authority left behind.** Either the old component holds funds (Notional V1 retained about \$60,600 after the drain), or it holds only standing approvals or permissions (ether.fi AtomicQueue held no funds and was drained of what it was still authorised to move).
- **Current version unaffected.** The operator or reporters state that the current version was not involved (Notional's current version, ether.fi's eETH, weETH and current Liquid vault positions, IPOR's current Fusion vaults).
- **Operator language pointing at the old component.** Statements such as Bullpen's "legacy system" or IPOR's confinement of the issue to legacy vaults identify the component as superseded.
- **Long idle time.** The exploited code had gone unused for years (the MakerDAO keeper's functions were not called for six and a half years; Aztec's products were deprecated in 2022 and 2023).

## Detection signals

- **Pre-incident: inventory of every superseded component (highest-leverage).** List every old version, keeper, queue, locker, beta service and replaced contract that is still deployed or running, with an owner and an end date. The question is not only "does it still hold assets?" but also "what is it still authorised to move, and who granted that?"
- **Pre-incident: approval and permission enumeration.** For each replaced contract, enumerate the ERC-20 approvals, operator roles and vault permissions that point at it (ether.fi, Limit Break and Troves-style cases), and confirm that revocation happened at replacement time.
- **Pre-incident: version-delta audit.** For every fix shipped in the current version, check whether the superseded version remains exposed (IPOR's legacy vaults predated stricter fuse validation; Notional V1 was never audited against V2's fixes).
- **Pre-incident: monitoring of dormant contracts.** Watch old contracts that hold value for the first state-changing call after a long idle period.
- **At-incident: first call into a long-idle legacy contract.** The MakerDAO and Notional examples each began with a single transaction against a contract that had seen no recent business.

## Mitigations

- **Decommission what the product no longer uses (highest-leverage).** Enforced by the operator's release process: each replacement ships with a decommissioning task that has an owner and a date, covering disabling deposits, migrating funds and sweeping the remainder. Notional's V1 escrow ([`examples/2026-09-notional-finance-v1-escrow-uint128-downcast-liability-truncation.md`](../examples/2026-09-notional-finance-v1-escrow-uint128-downcast-liability-truncation.md)) was left funded and reachable after V2, and the example describes it as a decommissioning task with no owner.
- **Revoke roles and approvals at replacement time and prove it on-chain.** Enforced in the migration script: after a contract is replaced, check that the old address holds no vault roles and that users are told to revoke approvals. A Troves replaced rebalancer kept its vault permissions, per [`examples/2026-10-troves-legacy-rebalancer-retained-permissions-xwbtc-vault.md`](../examples/2026-10-troves-legacy-rebalancer-retained-permissions-xwbtc-vault.md); the ether.fi AtomicQueue was drained through approvals never revoked ([`examples/2026-09-etherfi-legacy-atomicqueue-solver-access-control-approval-drain.md`](../examples/2026-09-etherfi-legacy-atomicqueue-solver-access-control-approval-drain.md)).
- **Drain reserves before abandoning an immutable contract.** Enforced before the last admin right is relinquished. Aztec's deprecated bridges could not be patched or paused, so the only control was emptying them first ([`examples/2026-06-aztec-deprecated-rollup-forged-proof-cohort.md`](../examples/2026-06-aztec-deprecated-rollup-forged-proof-cohort.md)).
- **Version-delta audit.** Enforced in the audit scope for each new version: for every fix in the new version, check whether the old one stays exposed. IPOR's legacy vaults predated stricter fuse validation ([`examples/2026-01-ipor-fusion-plasmavault-eip7702-admin-delegation-malicious-fuse.md`](../examples/2026-01-ipor-fusion-plasmavault-eip7702-admin-delegation-malicious-fuse.md)).
- **Shut down beta and test services, and purge the keys they hold, when the product moves on.** Enforced by the operator's decommissioning process: an inventory of every system that can reach user keys or sessions, with an owner and an end date. At Bullpen (2026-11-24) a legacy system from the April–June 2024 beta was still running and still tied to 19 accounts; it was shut down only after the unauthorized transfers ([`examples/2026-11-bullpen-early-beta-legacy-service-imported-solana-key-drain.md`](../examples/2026-11-bullpen-early-beta-legacy-service-imported-solana-key-drain.md)).

## Discussion

T11.013 sits at the boundary between OAK-T11 (operator-side operational practice) and OAK-T9 (the vulnerability class used). It is classified under T11 because the load-bearing condition is that an old component was left deployed and reachable, not which flaw was then used.

The lead example is the MakerDAO legacy auction keeper because its Root-cause evidence is `corroborated` (CertiK's transaction-level analysis, with Defimon independently flagging the missing access check), and the legacy component is central to it: the keeper had been dormant since 2020, held the collateral of four never-settled Black Thursday auctions (200 ETH), and one function never checked its caller. The example records that nobody called that function for six and a half years.

The declaring examples differ in how well they fit, and the page does not claim a uniform pattern. Notional declares T11.013 as primary; DxSale, Aztec, ether.fi and IPOR make the legacy component part of the mechanism; THORChain, Secret Network, Limit Break and Bullpen are weaker or contextual fits (see each file's own text). The earlier version of this page rested on GMX V1 and Yearn V1; neither example file declares T11.013 now (GMX's operator write-up gives cross-contract reentrancy, OAK-T9.005), so neither is used here.

The Technique is structurally adjacent to T9.007 (Fork-Substrate Vulnerability). Both involve deployed code that missed a fix. The distinction is organisational: T9.007's gap is between two teams, T11.013's is inside one team's version-lifecycle management. The mitigation differs accordingly: downstream fork operators monitor upstream disclosures, while a T11.013 operator needs its own decommissioning discipline.
