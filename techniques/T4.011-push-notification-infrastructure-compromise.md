# OAK-T4.011 — Push-Notification Infrastructure Compromise

**Parent Tactics:** OAK-T4 (Access Acquisition)
**Maturity:** emerging
**Chains:** cross-chain (the notification channel is off-chain; the loss lands on whichever chains the app's users hold funds on)
**First documented:** 2024-06 (CoinStats: a scam notification sent through the app's own push and in-app channels during a wider breach)
**Aliases:** "push-notification hijack", "in-app notification phishing", "notification-channel takeover"

## Description

An attacker gains the ability to send messages through the channel a wallet or crypto app uses to reach its own users (mobile push notifications, in-app banners) and uses it to deliver a phishing lure. The message arrives under the app's name and icon, from the app the user already installed, so the usual advice ("check who is writing to you") does not help.

The channel is usually run by a third party, and the credential that controls it is an API or access key. In the best-documented case, Ngrave says attackers hijacked the third-party provider that sends push notifications for its LIQUID app, used one access key to obtain a second with broader permissions, and sent a fake security alert by push notification and in-app banner ([Ngrave report](https://www.ngrave.io/en/blog/incident-report-fake-liquid-security-alert-17-october); [`examples/2026-10-ngrave-liquid-push-notification-channel-seed-phrase-phishing.md`](../examples/2026-10-ngrave-liquid-push-notification-channel-seed-phrase-phishing.md)). The vendor's wallet software and hardware were not breached; the notification channel alone was enough.

The notification is the entry step, not the theft. What takes the money is whatever the lure leads to: in the Ngrave case a counterfeit site that asked for the recovery phrase (OAK-T11.007.003); in the CoinStats case a link that CryptoSlate describes as leading to a drainer website ([CryptoSlate](https://cryptoslate.com/coinstats-suspends-app-after-security-breach-compromises-1590-wallets/)).

T4.011 is distinct from:

- **T4.008 (Fake-DEX Clone-Frontend Phishing)**: there the user navigates to an attacker-controlled site. Here the lure is pushed to the user through the vendor's own channel.
- **T11.002 (Wallet-Software Distribution Compromise)**: there the attacker changes the software the user runs. Here the software is untouched and only the message channel is abused.
- **T15.004 (Operator-Side Credential Compromise)**: the general class of stolen operator credentials. T4.011 records the specific case where the credential controls user-facing notifications; an incident can declare both.

**Correction, 2026-11-27.** Until this date the page described a CoinStats "malicious MetaMask Snap" distributed through a push notification as the canonical case. No source says a Snap was involved, and the 1,590 CoinStats wallets were drained through stolen private keys, not through the notification (see [`examples/2024-06-coinstats-wallet-infrastructure-breach.md`](../examples/2024-06-coinstats-wallet-infrastructure-breach.md)). The text about Snap distribution, and the detection and mitigation items built on it, were removed.

## Observed indicators

- A notification from the app that announces a security event or a reward and asks the user to act at once. Ngrave's fake alert claimed the portfolio had synced with an unknown device; the CoinStats notification announced a 14.2 ETH prize ([CryptoSlate](https://cryptoslate.com/coinstats-suspends-app-after-security-breach-compromises-1590-wallets/)).
- The link in the notification leads to a domain that is not the vendor's and asks for a recovery phrase or a wallet connection.
- The same message reaches many users at once, by push and by in-app banner.
- On the vendor side: notification-provider access from an unknown party, or a new access key created from an existing one. Ngrave dates the earliest attacker activity at its provider to 2026-10-11, six days before the alert.
- Drains of unrelated users' wallets clustered within minutes of the broadcast. Ngrave's first wallet was emptied six minutes after the alert.

## Detection signals

- **Provider-side audit log.** Alert on creation of new access keys, on permission changes, and on any broadcast to the whole user base that was not scheduled through the vendor's normal release process.
- **Canary devices.** Keep test devices subscribed to production notifications and alert on any message the vendor did not schedule. Ngrave noticed the fake alert one minute after it was sent.
- **Outbound link check.** Flag any notification whose link target is outside the vendor's own domains.
- **User reports.** A burst of support requests and social posts about one notification is often the first public signal; in the CoinStats case outlets reported the scam notification on the day it was sent.
- **On-chain clustering.** Wallets of many users of one app drained into a small set of collecting addresses within the same hour.

## Real-world examples

- [`examples/2026-10-ngrave-liquid-push-notification-channel-seed-phrase-phishing.md`](../examples/2026-10-ngrave-liquid-push-notification-channel-seed-phrase-phishing.md) — Ngrave LIQUID, 2026-10-17. Lead example: the operator's own report states the mechanism. About \$2.56M from about 70 addresses on four networks per Ngrave; about \$2.65M across 84 wallets per Bitquery as relayed by CryptoSlate.
- [`examples/2024-06-coinstats-wallet-infrastructure-breach.md`](../examples/2024-06-coinstats-wallet-infrastructure-breach.md) — CoinStats, 2024-06-22. Partial fit. A scam notification went out by push and in-app message to iOS and Android users during the breach and led to a drainer site ([CryptoSlate](https://cryptoslate.com/coinstats-suspends-app-after-security-breach-compromises-1590-wallets/)); The Block says the attacker sent fraudulent notifications to mobile users ([The Block](https://www.theblock.co/post/305167/coinstats-says-2-2-million-worth-of-crypto-was-stolen-in-june-hack-by-sophisticated-attacker)). The \$2.2M loss came from stolen private keys (OAK-T15.004). How the attacker reached the notification channel, and what the notification itself cost users, are undisclosed.

## Reference implementations

- `mg-detectors-rs`: coverage gap. The detection surface is the notification provider's audit log and the vendor's own monitoring, both off-chain.

## Mitigations

- **Least-privilege notification keys.** Enforced at the notification provider: a key that can send must not be able to create other keys or change permissions. At Ngrave the attacker used one key to obtain a second, more powerful one ([`examples/2026-10-ngrave-liquid-push-notification-channel-seed-phrase-phishing.md`](../examples/2026-10-ngrave-liquid-push-notification-channel-seed-phrase-phishing.md)).
- **Two-person approval for broadcasts.** Enforced in the vendor's notification tooling: no push or in-app message to the user base goes out on one person's or one key's authority. This is on Ngrave's own remediation list.
- **Key rotation and a kill switch.** Enforced by the vendor's operations: rotate provider keys on a fixed schedule (Ngrave committed to at least every 90 days) and keep one switch that stops all sending. Ngrave cut off the first key ten minutes after the alert, but sending continued through the second key for another 65 minutes.
- **No action links in security notifications.** Enforced in the app: a security notification opens a fixed screen inside the app and never an external URL, so a hijacked channel cannot route users to a counterfeit site.
- **User-side rule.** A wallet vendor never asks for a recovery phrase. Any notification that leads to such a request is phishing, whatever app it came from.

**Canonical mitigations:** OAK-M18, OAK-M22.

## Discussion

The Technique stays `emerging` because one incident (Ngrave) has an operator report that states the mechanism, and one (CoinStats) is a partial fit. Two further reports were found in the 2026-11-27 source pass and are not filed as examples: a Coins.ph incident of March 2026 in which the operator said unauthorized email and push notifications with phishing links went out through its messaging provider, with no loss reported; and an October 2026 report of a scam notification from the SecuX app whose origin was not established. They are candidates, not evidence.

The value of the page for a defender is the control point. The notification provider is rarely treated as part of the wallet's security boundary, because it cannot sign transactions. Ngrave shows that it does not need to: a message under the vendor's name is enough to get recovery phrases from some users, and the loss follows within minutes.
